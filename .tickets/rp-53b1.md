# Plan Docling GPU PDF conversion wrapper and skill

Intent/problem statement: plan and implement, after user clarification, a local Docling-based PDF conversion capability in this read-pdf workspace and install/adapt the upstream Docling document-intelligence agent skill into Codex skill format. The workflow target is LLM-consumable output for complex policy/economics PDFs: Markdown, Markdown with embedded images and structured tables, HTML with embedded images in reading order, and optionally DoclingDocument/DocTags/JSON intermediates.

Scope under consideration:
- Install/adapt the Docling document-intelligence agent skill from the Docling examples site into a Codex-compatible skill location.
- Add a small wrapper/CLI around Docling conversion for PDF to Markdown, embedded-image Markdown, structured-table HTML, and clean reading-order HTML.
- Evaluate CUDA/RTX setup and fail-fast GPU diagnostics.
- Enable OCR where needed for scanned content or tables pasted as bitmaps.
- Consider picture classification, picture description, code/formula enrichment, table-structure alternatives, and VLM conversion.
- Compare TableFormer table structure against Granite Vision / VLM-based table understanding on the sample94_strict_pdf set from opendataloader.

Explicit non-goals until clarified:
- Do not commit to a single all-features-on Docling pipeline if Docling exposes these features through incompatible conversion modes.
- Do not replace the existing read-pdf visual rendering workflow without evidence that Docling artifacts are better for the targeted PDFs.
- Do not mutate unrelated dirty files already present in the working tree.

Current analysis hypothesis: some requested features are likely mode-specific rather than additive. Standard Docling PDF conversion can export DoclingDocument/Markdown/HTML/JSON and use TableFormer, OCR, picture classification/description, and code/formula enrichment. VLM Convert with Granite-Docling-258M is a separate conversion path that emits Docling structure from a VLM, and VLM-based table structure with Granite Vision is likely a comparison lane rather than a flag inside the same standard TableFormer pipeline. Picture description with Granite Vision may require a separate picture-description model configuration and may not support the exact 4.1-4B model out of the box.

Approved implementation plan and user elections:
- Install/adapt the upstream Docling document-intelligence skill in the machine-global skills tree. Use `/home/safonso/machine-setup/.agents/skills/docling-document-intelligence/` and make it discoverable from `/home/safonso/.codex/skills/`.
- Build the wrapper as both a stable CLI and an experimental benchmark/analysis tool. Stable entrypoint should be under `scripts/`; implementation may live under `benchmark/pdf/` to keep comparison/profiling surfaces explicit.
- Default image policy is referenced images, not embedded base64. Embedded Markdown/HTML may be produced as optional artifacts.
- Initial comparison scope is a small smoke first, not the full sample94 set.
- First-pass table/comparison lanes: 3 lanes. Use standard TableFormer, VLM Granite-Docling-258M, and a Granite Vision lane. Also run both small and large Granite vision models where feasible to learn the time versus accuracy/effectiveness tradeoff.
- OCR default: OCR on, force OCR off. Prefer fail-fast CUDA diagnostics. Use RapidOCR torch backend when available/appropriate, but keep the wrapper robust to Docling defaults.
- Model cache/download policy: approved to download Docling/Hugging Face model artifacts into the local cache.
- Picture description: use `ibm-granite/granite-vision-3.3-2b` for Granite picture descriptions.
- Quantization: use a quantized mode if available for Granite Vision runs.
- No chart-extraction enrichment in this wrapper pass.
- Code/formula enrichment should be enabled in all conversion/profile cases that support it.
- Success on sample94 is not a formal benchmark. The objective is to determine whether any combination comes close to accurate on the hardest edge cases. Track runtime, page count, table count, picture count, image asset count, Markdown/HTML/JSON token size if cheap, likely bitmap-table evidence, conversion failures, reading-order sanity, and qualitative accuracy/effectiveness against difficult tables/images.

**2026-06-18T13:51:10Z**

2026-06-18 design conclusion: For the intended LLM-facing bitmap-first output, accurate-enough table/figure detection can mostly avoid GPU-demanding VLM/picture-description/classification models. Standard Docling layout/table detection plus OCR, provenance/page-width crops, and deterministic geometry/caption heuristics should be the default safe lane. This preserves high recall for substantive complex tables/figures but gives up VLM semantic interpretation: no reliable table cell reconstruction for bitmap/complex tables, weaker distinction between bitmap tables vs figures when captions are absent, no chart-to-data extraction or diagram descriptions, and less robustness to missed/fragmented picture boxes. Bias policy toward conservative bitmap retention because false positives cost tokens while false negatives lose content.
