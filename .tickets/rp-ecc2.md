# Add canonical PDF bundle pipeline and evaluation

Intent/problem statement: implement and evaluate a production-style canonical bundle pipeline for PDFs with complex tables and images, based on the table/image benchmark findings. The pipeline should containerize the conversion stack and return a canonical host artifact bundle suitable for LLM ingestion. It should also produce writeups comparing quality and token cost against source-PDF-as-images ingestion.\n\nScope:\n- Write an initial detailed report capturing the current method recommendation: Docling/OpenDataLoader for structured table JSON, PyMuPDF page renders/geometry as visual ground truth, PyMuPDF4LLM Markdown for readable fallback, MarkItDown and others as lower-priority comparison lanes.\n- Implement a locally runnable CLI command that invokes containerized conversion binaries and writes a canonical bundle back to the host.\n- The canonical bundle should include page-centered text/markdown, page renders, detected/extracted images, table JSON/HTML/Markdown where available, manifests, quality flags, and token-estimate artifacts.\n- Evaluate the bundle on one Article IV, one IPF, and one DPF source document. Use existing local corpora where possible and include P162302 PAD/IPF and the prior DPF/Article IV assets where applicable.\n- Compare token counts for canonical bundle, canonical bundle plus optional cheap-ish Gemini 3 Flash cleanup pass if convenient/available, and source PDF as images using the existing read-pdf image-token calculation logic for OpenAI/Gemini models.\n- Produce a final writeup with quality-vs-token tradeoff analysis and recommendations: first best, and second best if multimodal full-PDF/image ingestion is blocked.\n\nNon-goals:\n- Do not replace the earlier text benchmark or table/image comparator.\n- Do not run broad unrelated test suites.\n- Do not require cloud cleanup if Gemini 3 Flash is unavailable or inconvenient locally; record a clear blocker and still produce canonical/no-cleanup comparisons.\n\nRisks/tradeoffs:\n- Full Docling/OpenDataLoader extraction can be slow; bounded page selection may be needed for the evaluation.\n- LLM cleanup availability depends on local CLI/model configuration.\n- Token counts are estimates and must clearly state whether they count serialized payload text, rendered images, or both.\n- Some engines extract embedded logos/figures but not page-layout bitmaps, so PyMuPDF page renders remain mandatory for visual grounding.

## Acceptance Criteria

1. A detailed findings/report markdown exists with the recommended pipeline and engine roles.\n2. A locally runnable CLI command exists that runs the canonical bundle stack through containers and writes host artifacts.\n3. The bundle artifact layout includes page text/markdown, page renders, images, table artifacts, manifests, and token summaries.\n4. Evaluation runs cover Article IV, IPF, and DPF examples.\n5. Token comparison table includes rows for document type and columns for canonical bundle, canonical bundle plus cleanup if available, and PDF-as-images.\n6. Final report includes quality-vs-token analysis plus first-best and second-best recommendations.\n7. Focused tests/smokes verify CLI argument parsing, bundle artifact generation, token calculation, and at least one end-to-end run or a proven container/tool blocker.
