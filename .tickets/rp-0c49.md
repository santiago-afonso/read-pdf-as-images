# Correct canonical payload token accounting

Intent/problem statement: fix the canonical PDF bundle overhead comparison so it reflects the intended frankenstack payload, not the stored audit bundle. The intended LLM payload should be structured text/HTML/JSON plus content-relevant assets only, not every full-page render plus every embedded bitmap.\n\nScope:\n- Separate stored bundle/audit artifacts from LLM payload accounting.\n- Keep full page renders available on disk as optional visual ground truth, but exclude them from default LLM payload token counts.\n- Filter image assets to content-relevant figures/charts/diagrams/tables where possible, excluding likely stationery/logos/small decorative bitmaps.\n- Regenerate full-document token tables for DPF, IPF/PAD, and Article IV with corrected columns.\n- Update reports and tests so the distinction is explicit.\n\nNon-goals:\n- Do not build a perfect visual classifier for all charts/diagrams. Use transparent heuristics and report limitations.\n- Do not discard page renders from disk; they remain useful for audit and targeted fallback.\n\nRisks/tradeoffs:\n- Pure PDF embedded-image heuristics can miss vector charts/tables because many charts/tables are not embedded raster images.\n- If a figure is vector-only, the asset extraction may require targeted page/table crops later; this correction should still avoid counting every full page render.

## Acceptance Criteria

1. Token comparison exposes intended LLM payload counts that exclude full page renders by default.\n2. Stored/audit bundle counts remain available or clearly documented separately.\n3. Reports explain that full page renders are optional fallback artifacts, not the default payload.\n4. Full-document comparison is regenerated or recomputed for DPF, IPF/PAD, and Article IV.\n5. Focused tests pass.
