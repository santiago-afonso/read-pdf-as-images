# Review Docling bitmap routing and payload budget

Intent/problem statement: review and improve the read-pdf Docling conversion wrapper so LLM-facing Markdown+bitmap bundles have lower false negatives (complex or visually fragile tables incorrectly emitted as semantic HTML or omitted) and lower false positives (page furniture/icons/logos retained as substantive bitmap assets), while staying safely below the Azure OpenAI Batch API's 200 MB per-file/request constraint after HTTP framing, prompt, and schema overhead. User outcome: preserve visual authority for deleted/merged/spanning/multipage table layouts without routinely sending decorative assets or oversized bundles. Technical scope: inspect scripts/pdf-docling-convert and benchmark/pdf/docling_convert.py; audit a guided sample of existing DPF/PER/PforR/IPF/IMF/sample94 artifacts with a Terra/Luna subagent; review table-complexity and picture-retention heuristics, page-continuation fallback, bitmap encoding/resolution, manifest telemetry, and batch/runtime controls; implement narrowly scoped high-confidence improvements if evidence supports them; assess an optional second-pass Granite-Docling small VLM route on only risky pages and whether it materially changes bitmap selection; add deterministic preflight size estimation and a safe mechanical fallback design if the LLM bundle would exceed budget. Non-goals: no exhaustive review of thousands of PDFs; no production-scale laptop CUDA batch; no default Granite Vision 4B route; no full unrelated refactor; no Azure batch submission; do not rely on structured table cells as authoritative where PDF geometry is fragile.

## Design

Review mechanism first: (1) map current decision functions and artifact contract; (2) stratified artifact audit covering known complex tables, multipage tables, merged cells, captionless/bitmap tables, true figures, and furniture; (3) identify root causes and severity-ranked findings; (4) implement only fixes that reduce classification error without uncontrolled token/byte growth; (5) measure bundle bytes, number/area of retained bitmaps, and fallback behavior on focused fixtures. Payload policy should reserve explicit headroom below 200 MB for multipart/base64 expansion, prompt, schema, and provider metadata; raw on-disk asset bytes are not the same as HTTP request bytes. Prefer page/table JPEG or WebP only if provider support and legibility are verified; otherwise optimized PNG/JPEG with measured encoded request size. Granite-Docling small is an optional second-pass diagnostic for risky pages, not assumed to repair table geometry. Recommended canonical safety rule: if table structure is uncertain, send the source bitmap; if the bundle is oversized, preserve text plus a ranked subset of visually risky pages and record an explicit omission/fallback manifest rather than silently downgrading.

## Acceptance Criteria

Findings are reported first with absolute file/line references and distinguish verified defects from hypotheses; artifact audit records sampled paths and evidence; focused changes, if any, have tests for deleted/merged/spanning cells, multipage continuation, furniture suppression, and payload-size budgeting; current Docling 2.111 standard smoke remains green; size logic demonstrates a conservative request budget below 200 MB that accounts for encoding/HTTP/prompt/schema headroom; optional VLM recommendation is supported by measured quality/runtime evidence rather than assumption; ticket notes list files touched, checks run, risks, rollback, and residual false-negative/false-positive cases.
